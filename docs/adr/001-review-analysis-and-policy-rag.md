# ADR-001: 검증된 SQL Tool과 정책 Hybrid RAG의 분리

[English](001-review-analysis-and-policy-rag_EN.md) · [메인 문서](../../README.md)

## 상태

Accepted

## 한눈에 보는 결정

Customer Intelligence Agent가 사용하는 근거는 성격이 다르므로 하나의 검색 방식으로
통합하지 않습니다.

| 질문과 데이터 | 실행 경로 | 시스템이 보장하려는 것 |
|---|---|---|
| 상품, 평점, 리뷰 수, 날짜와 반복 불만 | 검증된 PostgreSQL Tool | 정확한 필터·정렬·집계와 리뷰 원문 추적 |
| 환불, 재배송, 보상, 예외 승인과 CS 절차 | 권한 필터가 적용된 정책 Hybrid RAG | 현재 사용자에게 적용 가능한 최신 정책 근거 |
| 고객 불만과 처리 기준을 함께 묻는 질문 | SQL Tool과 RAG 결과를 분리 조회한 뒤 Agent가 결합 | 고객 경험과 운영 규칙의 출처를 혼동하지 않는 답변 |

핵심 원칙은 다음과 같습니다.

> **숫자와 데이터 선택은 결정론적 코드가 담당하고, 문서 의미 검색과 설명은 제한된
> 범위에서 모델을 사용한다.**

## 해결하려는 문제

리뷰 통계와 사내 정책은 모두 자연어 질문에 필요하지만 요구되는 정확성이 다릅니다.

- 리뷰 수, 평점 비율과 날짜 조건은 정확한 계산이 필요합니다.
- 정책은 같은 의미가 서로 다른 표현으로 작성되어 키워드 일치만으로 찾기 어렵습니다.
- 리뷰는 고객 경험의 근거이지만 정책·의학·안전 기준을 증명하지 않습니다.
- 정책은 허용된 조치를 설명하지만 실제 고객 불만의 빈도를 보여주지 않습니다.

모든 데이터를 Vector 검색이나 하나의 LLM Prompt에 맡기면 수치의 재현성, 정책 적용
범위와 근거 출처가 섞일 수 있습니다. 따라서 두 경로의 책임을 분리합니다.

## 선택한 구조

```text
사용자 질문
  ↓
Agent: 질문 의도와 필요한 근거 판단
  ├─ 리뷰 분석 경로
  │    → 검증된 SQL Tool
  │    → PostgreSQL 표본·통계
  │    → 필요 시 Aspect Extractor와 Python 검증·집계
  │
  ├─ 정책 RAG 경로
  │    → 권한·유효기간·적용 범위 필터
  │    → Child FTS + Embedding 검색
  │    → Parent 기준 RRF
  │    → BGE-M3 MaxSim 재정렬
  │    → 정책 우선순위와 LLM 근거 판정
  │
  └─ 복합 질문이면 두 결과를 출처별로 결합
       ↓
정량 지표, 리뷰 원문과 정책 근거를 구분한 답변
```

Agent는 SQL을 직접 작성하지 않습니다. 질문에 맞는 Tool을 선택할 뿐이며, 실제 조회
조건과 집계는 사전에 구현하고 테스트한 코드가 수행합니다.

## 경로 1: 고객 리뷰 분석

| 단계 | 책임 |
|---|---|
| Tool 선택 | Agent가 상품 조회, 평점 분포, 저평점 리뷰 또는 반복 불만 Tool을 선택 |
| SQL 조회 | PostgreSQL이 코드에 정의된 조건으로 표본과 통계를 반환 |
| 의미 추출 | 반복 불만 질문일 때 Extractor가 리뷰별 Aspect·감성·근거 구절을 구조화 |
| 코드 검증 | Python이 근거 구절의 원문 포함 여부와 허용 taxonomy를 확인 |
| 집계 | Python이 고유 리뷰 수, 표본 내 비율과 평균 confidence를 계산 |
| 답변 | Agent가 검증된 Tool 결과만 사용하여 현업 관점으로 설명 |

이 경로는 LLM이 임의의 테이블·조건·숫자를 생성하는 위험을 줄입니다. Aspect 분석의
스키마, Redis 캐시와 리뷰별 호출의 한계는 [고객 리뷰 분석 문서](../review-analysis/README.md)에
정리했습니다.

## 경로 2: 사내 정책 Hybrid RAG

| 단계 | 책임 |
|---|---|
| 사전 필터 | 승인 상태, 유효기간, 상품, Collection, 관할, 부서와 사용자 권한 적용 |
| Child 후보 검색 | PostgreSQL FTS `ts_rank_cd`와 Embedding cosine 검색을 독립 수행 |
| Parent 통합 | 검색된 Child를 Parent 정책 섹션으로 복원하고 RRF로 순위 결합 |
| 정밀 재정렬 | BGE-M3 ColBERT MaxSim으로 질문 토큰과 Parent 토큰을 비교 |
| 정책 우선순위 | 상품 전용 여부, Authority Tier와 시행일을 Python 규칙으로 비교 |
| 근거 판정 | 구조화 LLM이 `sufficient / insufficient / conflict`만 판정 |
| 답변 제한 | 충분한 Parent만 인용하고, 판정 실패나 근거 부족은 `no_evidence`로 종료 |

FTS는 정확한 정책 용어를 찾고 Embedding은 표현이 다른 의미를 보완합니다. RRF는 두
채널의 점수 체계를 직접 비교하지 않고 순위만 결합합니다. BGE-M3는 전체 문서를
검색하는 1차 검색기가 아니라, 좁혀진 Parent 후보를 토큰 수준에서 비교하는 2차
재정렬기입니다. 상세 후보 수와 MaxSim 계산은 [정책 RAG 문서](../rag/README.md)를
참고합니다.

## 시스템 불변조건

모델 성능과 무관하게 다음 조건은 코드에서 강제합니다.

| 불변조건 | 구현 원칙 |
|---|---|
| SQL 정확성 | LLM 생성 SQL을 실행하지 않고 검증된 Tool만 허용 |
| 수치 Grounding | Tool 결과에 없는 수치와 비율을 만들지 않음 |
| 리뷰 원문 근거 | Extractor evidence가 실제 리뷰에 포함되는지 Python으로 확인 |
| 정책 접근 통제 | 사용자 권한과 정책 범위를 검색 전에 서버에서 적용 |
| 정책 충돌 | 동일 우선순위의 상충 정책을 Agent가 임의 선택하지 않음 |
| 의료·안전 | 일반 답변 경로를 중단하고 사람의 검토로 escalation |
| 검색 실패 | Reranker 오류는 RRF로 복귀하고, 근거 판정 실패는 fail-closed 처리 |

## 대안과 채택하지 않은 이유

| 대안 | 결정 | 이유 |
|---|---|---|
| 모든 데이터를 Vector DB에서 검색 | 채택하지 않음 | 정확한 개수·비율·필터·정렬을 보장하기 어렵고 관계형 데이터의 장점을 잃음 |
| LLM이 질문마다 SQL을 생성 | 채택하지 않음 | 스키마·조건 오류와 집계 기준 변동 가능성이 커짐 |
| 정책을 FTS만으로 검색 | 채택하지 않음 | 문서와 질문의 표현이 다르면 관련 정책을 놓칠 수 있음 |
| BGE-M3 Dense·Sparse로 1차 검색까지 교체 | 채택하지 않음 | PostgreSQL FTS와 기존 Embedding의 후보 생성 역할과 중복되며 운영 복잡도가 증가 |
| Graph RAG·Neo4j 도입 | 현재 채택하지 않음 | 핵심 요구가 다단계 관계 추론보다 문서 검색과 구조화 집계에 있음 |
| 하나의 Prompt에서 통계와 정책을 모두 판단 | 채택하지 않음 | 숫자, 권한과 근거 출처를 모델 응답에 과도하게 의존하게 됨 |

## 운영 기본값

| 항목 | 기본값 | 의미 |
|---|---:|---|
| FTS 후보 | 10 | 채널별 Child 후보 수 |
| Embedding 후보 | 10 | 채널별 Child 후보 수 |
| Vector 최소 유사도 | 0.33 | 낮은 관련성의 Vector 후보 제거 |
| RRF 상수 | 60 | 채널 간 순위 차이 완화 |
| 최종 근거 후보 | 5 | 우선순위 처리 후 LLM 근거 판정에 전달할 Parent 수 |
| BGE-M3 입력 | 질문 256 / Parent 2,048 tokens | 재정렬 시 최대 입력 길이 |
| BGE-M3 batch | 2 | GPU 메모리를 고려한 처리 단위 |
| 근거 판정 timeout/retry | 15초 / 1회 | 실패 시 답변을 강행하지 않음 |

이 값은 정확성의 보편적 기준이 아니라 현재 데이터와 평가 세트에서 선택한 초기
운영값이며, 문서·질문 분포가 바뀌면 다시 평가해야 합니다.

## 결과와 한계

### 얻은 효과

- 정량 분석은 재현 가능한 SQL 결과로 설명할 수 있습니다.
- 정책은 권한과 유효기간을 반영한 근거만 Agent에 전달됩니다.
- 고객 경험과 정책 판단의 출처가 답변에서 분리됩니다.
- Reranker나 LLM 판정 실패가 근거 없는 답변으로 이어지지 않습니다.
- OpenAI와 로컬 모델을 같은 Tool·스키마·평가 계약으로 비교할 수 있습니다.

### 감수한 한계

- 두 검색 경로와 실패 처리를 별도로 운영해야 하므로 구성 요소가 늘어납니다.
- 최초 Aspect 분석은 캐시되지 않은 리뷰마다 LLM을 호출하여 지연과 비용이 큽니다.
- 고정 Aspect taxonomy 밖의 불만은 반복 패턴에 포함되지 않을 수 있습니다.
- BGE-M3 reranker가 가용하지 않으면 정책 검색은 RRF fallback에 의존합니다.
- LLM 근거 판정은 오류 가능성이 있으므로 충분한 근거가 없을 때 답변을 보류합니다.

## 재검토 조건

다음 조건이 발생하면 이 결정을 다시 검토합니다.

- 제품·정책·부서·예외 간 다단계 관계 추론이 핵심 요구가 됨
- 문서와 Chunk 규모가 PostgreSQL 검색 성능 범위를 크게 초과함
- 리뷰 taxonomy가 빈번하게 바뀌어 고정 스키마 유지 비용이 커짐
- 독립 reranker 운영 비용이 검색 품질 향상보다 커짐
- 평가에서 단일 검색 경로가 현재 이원화 구조와 같은 정확성·근거성을 보임
