# ADR-001: SQL 기반 구조화 데이터 조회와 문서 RAG의 결합

## 상태

Accepted

## 배경

Customer Intelligence Agent는 서로 다른 성격의 근거를 사용한다.

1. 상품, 리뷰, 평점, 날짜, helpful vote와 같은 구조화 데이터
2. 환불·재배송·보상·프로모션·CS SOP와 같은 비정형 사내 운영 문서

두 데이터는 검색 방식과 답변에서의 역할이 다르다.

## 결정

구조화 데이터는 PostgreSQL Tool로 조회하고,
사내 비정형 문서는 PostgreSQL Full Text Search와 pgvector를 이용한
Hybrid RAG로 검색한다.

Vector 검색에는 보정된 최소 관련성 기준을 적용한다. 기준 미달 후보는 제거하되
FTS에서 명확히 일치한 후보는 유지하며, 남은 후보가 없으면 `no_evidence`를
반환한다. 기본 cosine similarity는 0.33이고 운영 평가 결과에 따라 설정으로
조정한다.

PostgreSQL Hybrid Retrieval이 만든 후보는 BGE-M3의 multi-vector 출력만 사용해
ColBERT 방식으로 재정렬한다. 별도 multi-vector DB는 도입하지 않고 상위 후보를
애플리케이션에서 재정렬한다. 이후 LLM 구조화 판정이 질문에 직접 답할 근거인지
`sufficient`, `insufficient`, `conflict`로 판정한다. 최소 관련성 수치는 최종
답변 가능 여부를 결정하지 않는다.

Agent는 질문의 목적에 따라 다음 경로를 선택하거나 조합한다.

- 고객 경험과 수치 분석 → SQL Tool
- 사내 정책, SOP, 예외 승인 기준 → RAG Retriever
- 고객 불만 현황과 운영 정책 판단 → SQL Tool + RAG Retriever

## 선택 근거

### 구조화 데이터에 SQL을 사용하는 이유

리뷰 수, 평점 분포, 날짜 범위, helpful vote 정렬과 같은 조건은
정확한 필터링과 집계가 필요하다.

이를 벡터 검색으로 처리하면 다음 문제가 발생한다.

- 정확한 개수와 비율을 보장하기 어렵다.
- 필터와 정렬 결과가 불안정해진다.
- 원본 데이터 변경 시 임베딩을 다시 생성해야 할 수 있다.

### 사내 문서에 RAG를 사용하는 이유

사내 정책과 운영 절차는 같은 의미가 다양한 표현으로 나타나며,
사용자의 자연어 질문과 문서 표현이 정확히 일치하지 않을 수 있다.

따라서 키워드 검색과 임베딩 검색을 결합한 Hybrid Retrieval이 적합하다.

### 두 검색 방식을 결합하는 이유

고객 리뷰는 실제 고객 경험을 나타내지만,
성분의 안전성이나 법적 판단을 직접 입증하지 않는다.

사내 정책은 허용되는 운영 조치를 제공하지만,
특정 제품 사용자의 불만 빈도와 영향은 보여주지 않는다.

두 근거를 분리해서 조회하고 함께 제시해야
다음과 같은 분석이 가능하다.

- 반복 불만과 재배송·환불 기준 비교
- 고객 불만과 제품별 CS 가이드 비교
- 반복 클레임의 escalation 및 예외 승인 검토

## 대안 검토

### 모든 데이터를 Vector DB에 저장

채택하지 않음.

정확한 통계, 필터링, 정렬에 부적합하며
기존 관계형 데이터의 장점을 잃는다.

### 사내 문서를 SQL 키워드 검색만으로 조회

채택하지 않음.

표현이 다른 의미 기반 질문에 대한 검색 재현율이 낮아질 수 있다.

### Neo4j 또는 Graph RAG 도입

현재는 채택하지 않음.

다단계 관계 추론보다 문서 검색과 구조화 집계가 핵심이며,
별도 그래프 DB 운영 비용과 동기화 복잡도가 더 크다.

### BGE-M3 통합 Hybrid Retrieval로 전체 교체

채택하지 않음.

PostgreSQL FTS와 기존 OpenAI embedding 검색이 이미 후보 생성 역할을 수행한다.
BGE-M3의 dense와 sparse 출력을 중복 도입하지 않고, 세부 조건 대응을 개선하는
multi-vector ColBERT 기능만 제한적으로 사용한다.

## 최종 구조

사용자 질문
    ↓
LangGraph Agent
    ├─ PostgreSQL Review/Product Tools
    ├─ Internal Policy Hybrid Retriever
    │    └─ PostgreSQL 후보 → ColBERT 재정렬 → LLM 근거 판정
    └─ 필요 시 두 결과 통합
             ↓
고객 리뷰 근거와 내부 정책 근거를 구분한 답변

## 제약 사항

- 리뷰 내용만으로 의학적·과학적 인과관계를 확정하지 않는다.
- 만료 정책과 미래 시행 정책은 현재 정책으로 적용하지 않는다.
- 제품·관할·부서 적용 범위를 표시한다.
- 검색된 내부 정책 근거가 부족하면 조치를 확정하지 않는다.
- 동일 우선순위의 정책 충돌은 Agent가 임의로 해결하지 않는다.
- SQL 통계와 RAG 문서 근거의 출처를 별도로 표시한다.

## 향후 재검토 조건

다음 조건이 발생하면 Graph RAG 또는 별도 검색 인프라를 검토한다.

- 제품–정책–부서–예외 간 다단계 관계 추론이 핵심 기능이 됨
- 문서와 청크 규모가 PostgreSQL 검색 성능 범위를 크게 초과함
- 관계 추론 정확도가 일반 Hybrid Retrieval보다 중요한 요구사항이 됨
